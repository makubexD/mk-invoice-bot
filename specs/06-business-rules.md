# 06 · Business rules, user messages and capability gaps

Every time the bot stops, warns or changes route, it does so because of **one named rule**. Each rule has:

- an ID (`BR-…`);
- a condition;
- the resulting state;
- the exact chat message (es-PE). Messages live in code as a catalog: `rules/catalog.py` maps each rule ID to its state and message key, and `rules/messages_es.py` holds the texts. Both are keyed by rule ID, so they are testable and easy to reword.

When the root cause is something **missing from the repository** (a portal, a parsing rule, a template mapping), the rule also raises a **capability gap** (§3). In the MVP the gap opens an issue in the private ops repo and alerts the owner in chat (D44). A PR from a template comes as the last v1 step (S16.2, D52); red-CI watches are post-MVP.

Placeholders like `{razon_social}` are filled from the invoice. Messages stay short: one idea, one action.

`{buyer_desc}`: `del RUC 20… (Razón social)`, `del DNI 4…`, or `de ningún cliente (boleta sin datos)`.

`{tipo_desc}` in a sentence (BR-R08, BR-E05) is `una factura`, `una boleta`, `una nota de crédito` or `una nota de débito`, and `otro tipo de documento (código 09)` for any other type. `{accepted_desc}` lists the flow's types in the plural: `facturas`, `facturas y boletas`.

**Summary message.** A routed invoice gets one summary (R-3.4). Since D206 it goes out after the first fetch attempt that does not move straight on to the next fetcher: an `ok`, a wait for a retry (BR-F13, `FETCH_WAITING`), a technical retry, the final failure (BR-F07), or a flow with nothing to fetch (D144); the step's own notice follows it. It is built from the reading as it is then, so a field the XML confirmed (D202) is not in `⚠️ Revisa`, and the buttons below follow that reading while an edit is still accepted; a summary that goes out with the move to `DELIVERING` (an `ok`, or nothing to fetch) carries none, since they are valid only until delivery starts (R-3.4). A question that waits (BR-E01, BR-V02, the `CONFIRMING` summary) still goes out at once. Its lines, in order:

1. `🧾 {tipo_desc} {serie}-{numero} · {fecha}`, where `{tipo_desc}` is `Factura`, `Boleta`, `Nota de crédito` or `Nota de débito` and `{fecha}` is `dd/mm/aaaa`;
2. `Emisor: {issuer}`, where `{issuer}` is `{razon_social} (RUC {ruc_emisor})` when the padrón gave a name, else `RUC {ruc_emisor}` (D188);
3. `Total: S/ {total}`;
4. `🔎 Leído de: {sources_desc}`: where the required fields came from, the source holding most of them named alone first, each other source as `{desc}: {fields_desc}`, `; ` separated, e.g. `QR` or `QR; texto: fecha, total` (D188);
5. the matched routing rule's own message, e.g. `➡️ {flow.label}` (BR-R01, BR-R02);
6. only when a field was repaired from the QR (D79): `ℹ️ Deducido del comprobante: {fields_desc}`;
7. only when a field is doubtful (low confidence, a failed R-2.4 check, or a date in the future or older than `max_invoice_age_days`): `⚠️ Revisa: {fields_desc}`. Until replies are handled (`widen-b`), the invoice goes on (D80).
8. only when the invoice goes on without waiting (not `CONFIRMING`): after an `ok` fetch, BR-F16's lines, `📄 Encontré {docs_desc}. Lo archivo…` and, when the XML cleared a field the reading's `⚠️ Revisa` named, `✅ El XML confirma: {fields_desc}`, with no buttons and no tap hint, since delivery starts in the same step (D206, R-3.4); otherwise `⏳ Busco sus archivos para archivarlo. Toca un botón solo si algo está mal.` (D188) when it carries buttons, else `⏳ Busco sus archivos para archivarlo.` (D189). Without `ok` the documents are not in hand yet, so it does not claim filing; the words match `/estado`'s `buscando sus archivos` (D190).

That summary carries [✏️ Corregir] [✖️ Anular], the same edit and cancel actions as [Editar] [Cancelar], worded so nothing reads as pending, and only when a required field was read from the printed text (source `ocr` or `llm`); a summary whose required fields all came from the QR, an XML, the padrón or the sender has no buttons, and `/cancelar {id}` still works (D189); a question that waits (BR-E01, the `CONFIRMING` summary) keeps [Editar] [Cancelar] (D188).

`{fields_desc}` names the fields in Spanish, comma separated: `fecha`, `tipo de comprobante`, `total`.

**BR-E01 partial text.** When extraction keeps a partial reading, BR-E01 names what it read and what is missing (D188), one piece per line: `Leí parte del comprobante #{id}.`, `✅ Leído: {read_desc}`, `❓ Falta: {missing_desc}`, `Envíame otra foto más cerca y con buena luz, o escríbeme solo lo que falta, un dato por línea:`, then `{missing_lines}`, one `{key}=…` line per missing field (`fecha=dd/mm/aaaa` for the date). `{read_desc}` is each read required field's name and value, `; ` separated; `{missing_desc}` is a `{fields_desc}`. It carries [Editar] [Cancelar].

## 3. Capability gaps

A **gap** is a missing capability that only a change to the repository can fix. Gaps are deduplicated by **fingerprint**, so 10 invoices from the same unknown store make **1** issue and **1** owner alert. Issues go only to the **private ops repo** (D44).

**Owner alert texts** (D116, `rules/messages_es.py`): `GAP_admin` `🧩 Falta configurar: {kind_desc} — {subject}.{issue_line}`, where `{issue_line}` is ` Issue: {issue_url}` once the issue exists, else empty. `GAP_DIGEST_admin` `🧩 Pendientes de configuración:` followed by one `• {kind_desc} — {subject}` line per gap. A gap is _raised_ (issue, alert) once, when its count first reaches the "Raised at" count; a kind with a window restarts its count when `last_seen` is older than the window (D115). With GitHub enabled the alert is sent when the issue opens, with its link; with GitHub disabled, when the gap is raised; a raised gap still without an issue after 24 h is alerted without a link by the daily digest task (R-11.11). Digest kinds go only into the daily `GAP_DIGEST_admin`.

A PR from a template that adds the missing `stores/` and `portals/` files comes at the end of development (S16.2, D52); the `gap-watch` workflow and the other draft PRs are post-MVP (D44, spec 04 E16).

**What is _not_ a gap:** expected business outcomes (flow B has no SOL access, an annulled invoice, a duplicate) and operations problems (expired OAuth tokens, SUNAT down, backups). Those get a chat message and, for operations, an admin alert, but nothing in GitHub.

### Gap lifecycle

```
detected ─► OPEN (row in `gaps`, linked invoices)
         ─► REPORTED (issue opened in the ops repo, owner alerted)
         ─► FIXED (the owner's fix is merged and deployed by CI; after the reload the re-check passes
                   → linked invoices re-enqueued, senders notified)
         ─► CLOSED (verified: a linked invoice got past the failing step, or none is left;
                    the bot closes the issue with a comment, `gap.closed`)
    OPEN/REPORTED ─► IGNORED (admin replies /gap ignorar <id>: no more alerts for this fingerprint)
```

If a re-enqueued invoice fails again at the same step, the gap goes back to REPORTED and the issue stays open. There are no "Closes #n" PRs in the MVP.

### What goes into GitHub (privacy)

Only typed **public or technical** data (R-11.12):

- issuer RUC (11 digits) and razón social from the padrón;
- CPE type;
- fetcher reason codes;
- the portal URL, reduced to `https://host/path`, in a code fence, and only once the owner approved it.

**Never:**

- buyer RUC or DNI, serie or número, totals, phone numbers, photos (one exception: an `UNROUTED_BUYER` issue names its buyer RUC in the title and marker, D120);
- counts, dates or anything else that reveals spending habits (they stay in the bot's database);
- raw OCR text, LLM text, or any text the user typed.

Gap issues go only to the private ops repo. These rules hold anyway, so a leaked issue reveals nothing about the owner's spending.
